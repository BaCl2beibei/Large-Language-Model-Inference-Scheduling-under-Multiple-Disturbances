# V304结果总结与主机CPU修复任务

日期：2026-11-09。将本文件交给Windows或Linux主机agent执行。先核对事实和本地训练历史，再依次修复物理模型、奖励标定、选模和训练覆盖。保持原生Windows/Linux CPU兼容。

## 一、当前结果与判断

### 1. 训练曲线

- 用户训练曲线显示：492次更新、1968个训练回合，选择的最优策略为第304版。
- 大约60–100次更新后，总体回报和C进入平台；继续训练到492次没有显著持续改善，图中未见总体指标发散。
- loss接近零不代表物理模型准确、每环境策略合理或真实效果通过；它也不足以证明Actor/Critic实现错误。
- 第304版只经历1216回合。若13环境等概率，NATIVE在该版本前的期望为93.54回合，全部1968回合中的期望为151.38回合。
- 服务端没有收到主机实际训练history。按默认seed133701重建得到105/164次只是条件推算，不能当实测覆盖。首先从主机实际checkpoint核对，不得直接下结论“NATIVE没训练到/训练次数太少”。

### 2. 同轨迹CPU复核与真实pilot

P1来自`development_evaluation.json`，是开发评估，不能称为独立留出测试。服务端用P2的计划到达trace、冻结模型和V304策略补跑同轨迹CPU闭环；PPO采用真实pilot的动作seed，但状态各自演化，不是强制相同动作回放。

C = mean E2E + CVaR95；下表单位秒，误差为仿真/真实−1。

| 环境 | 策略 | 同轨迹仿真C | 真实C | 有符号误差 |
| --- | --- | ---: | ---: | ---: |
| NATIVE | Stay | 206.37 | 118.61 | +73.99% |
| NATIVE | Balanced | 206.47 | 175.63 | +17.56% |
| NATIVE | PPO | 210.40 | 236.74* | −11.13% |
| HOT2-H | Stay | 256.88 | 256.01 | +0.34% |
| HOT2-H | Balanced | 219.53 | 226.61 | −3.13% |
| HOT2-H | PPO | 212.43 | 234.19 | −9.29% |

\* NATIVE/PPO虽48/48请求完成，但实际运行204.823秒、超过200秒，执行审计未通过；C仅作诊断，不进入正式宏平均和通过判定。C是两项延迟之和，C本身超过200秒不等于回合越窗。

固定真实NATIVE/Stay初始路由后，仿真C仍为207.03秒，说明分发差异不足以解释快慢差。当前有效cadence模型下界约61.45ms，真实NATIVE/Stay采样executor中位约32.82ms；模型缺失快速运行区间或其它运行状态。executor是抽样数据，不能当作逐Token客户端时间戳。

HOT2-H的Stay已非常准确，但仿真认为PPO比Balanced好3.23%，真实PPO反而差3.34%。验收基线绝对误差不足以保证干预收益、策略排名准确。

旧拟合表的C宏平均误差6.84%来自54次已见Stay/Balanced闭环；gain_C平均绝对误差仍为9.94个百分点，且HOT1-L/H部分配对符号错误。旧结果未覆盖每回合上百次重复迁移的PPO行为，正式ready当时也为false。

| 真实环境 | 成功迁移 | 涉及不同请求 | 重复迁移 | 单请求最多迁移 |
| --- | ---: | ---: | ---: | ---: |
| NATIVE | 118 | 32 | 86 | 20 |

有合法迁移时，策略输出的总迁移概率均值分别约98.28%、99.30%。对保存观测重算贪心动作，也均不选择Stay。Mask保证合法，不保证有收益；仅部署改argmax不能解决。

P1中PPO宏平均C只比Balanced好0.23%，但迁移111.5次对18.77次；NATIVE的PPO C已经比Stay差2.13%。当前按宏平均回报选模允许牺牲一个环境，尤其12个热点环境合计占12/13。

### 4. 热点阈值具体是什么、为什么需要改

它是奖励参数`hotspot_threshold = tau_H`：

```text
H = clip((max_j KV_used_fraction_j - tau_H) / (1 - tau_H), 0, 1)
B_star = H * 2 * std(KV_used_fraction)
```

当前`tau_H=0.001050788`，即0.105%占用，容量8565时约9 blocks。超过它才开始有热点惩罚，并非立刻最大惩罚。它影响热点奖励和均衡激活，不是迁移合法性阈值、冷却时间或Balanced控制器的阈值。

源标定只有24个正排队快照、2537个负快照、3个基础trace组；Youden J约0.01774、特异度1.77%，区分拥塞很弱。冻结只是固定数值，不代表可靠。低阈值不能单独证明过度迁移的全部原因；真实HOT2-H的V2回报也是Balanced更优，优先仍要修物理预测。

## 二、必须保留的合同

1. 四实例、13环境（12人工热点+NATIVE），沿用各环境已选N/QPS/强度；NATIVE继续参与训练，不改成未见环境。
2. 采样间隔1.5秒、PPO迁移冷却0秒；单迁移并发、容量/SR候选等合法Mask保留。不得用恢复固定冷却或迁移次数硬截断来隐藏问题。
3. 原始状态68值，归一化实例/全局/迁移对维度18/16/4；保持Stay+12对动作、共享策略。初轮修复不改变状态及网络结构。
4. 主动Stay参与Actor/Critic/GAE；全部迁移被Mask的强制Stay不参与Actor，保留Critic和连续GAE。
5. 每回合最多200秒仿真时间；未完成请求明确timeout、失败计奖惩、保留部分输出，正确终值；墙钟watchdog报错不能伪造成成功回合。
6. 时间折扣`.99**dt`、GAE`.97**dt`；四项核心奖励为时间、队列、热点、均衡。各项修改须单独版本化、做消融，不能同时乱调。
7. Windows原生Python和Linux CPU共用实现；不引入WSL要求、GPU框架依赖或Linux专属导入。
8. 旧V304、旧拟合与测试结果保留。新模型/奖励/源码生成新contract、manifest和包hash；不原地改冻结文件后伪称兼容。跨contract不能`--resume`或混用旧rollout/GAE；新训练默认从新V2初始策略开始。

## 三、执行顺序与修改要求

### A. 先审计主机已有训练记录

在实际解压目录定位`configs/local_train.json`、`runs/.../local_report.json`、`checkpoints/latest.pt`、`checkpoints/selected.pt`和`updates/`。

- 从`state.history`统计第304版前和全部训练的13环境覆盖；分别统计Actor有效决策、主动/强制Stay、迁移次数，而不只看回合数。
- 检查是否每更新4个同版本on-policy回合、实际采样seed/算法、失败回合保留和恢复行为。
- 汇总可用的KL、clip_fraction、总损失/Actor/Critic/entropy分项、梯度、优势分布和价值解释度；缺失字段明确标缺失，并补日志，不能编造收敛诊断。
- 检查是否有独立heldout报告；只有development文件不算完成留出验证。
- 此阶段可先实现日志和选模修复，不必等待物理重拟合。

### B. 重新拟合物理模型，先解释NATIVE快速Stay

使用已有真实数据，按batch、上下文、全局活跃实例/请求数、迁移阶段、GPU/服务运行条件分层看残差。现有强制非负线性截距会排除快速区间，允许比较有物理解释的分段或交互模型，但保持非负预测和统一时钟。

- 分开服务executor耗时、有效输出cadence、迁移传输/暂停/恢复；不能把聚合TPOT当单次Token间隔，也不能每Token重复计flush边界开销。
- 分别检查低压Stay、高压Stay、Balanced低频迁移、PPO高频与重复迁移。
- 保留原生路由闭环和固定真实初始路由两种诊断。进一步固定真实动作，分别用预测与观测迁移成本回放，定位剩余偏差。
- 判断迁移是否影响其它请求/实例的吞吐，别只对被迁移请求加暂停；同时排查执行顺序、服务/GPU状态漂移。Native六次Balanced迁移也慢48%，不能把全部差异都归为单次迁移暂停。
- 物理模型不得以环境ID、策略名、真实胜负查表修正速度/收益。样本不足的状态标为低置信度，不能强行外推成“已拟合”。
- 同时报告mean/p95/C、D/Q/H/B*、状态曲线及成对收益/排名。若预测差小于模型误差或测量噪声，应标“无法区分”，不能因C误差小于20%就声称几百分点策略优势可靠。
- 修改共享模型时，回归检查其余已有环境；不能只修两项而让其它环境退化。历史完整真实原始数据不在小证据包中时，列出所需来源；先完成可用数据的残差分析和代码修复，正式全池验收仍标未完成。

### C. 重新标定热点项，并显式检查迁移代价

- 把“瞬时waiting>0”与持续排队、容量不足或控制batch后速度下降区分开，重新定义标定标签。
- 按基础trace分组训练/验证，报告灵敏度、特异度、Youden J、支持样本及不确定性；不能把同一trace相邻快照当独立样本。
- 证据不足就标`weak/unidentifiable`。可以为开发做H/B降权或关闭的消融，但不得假装正式阈值已可靠，也不得随意改成80%。
- 先让时间模型如实体现迁移代价；再单独比较对测量暂停、复制blocks或重复/反向操作计成本的版本，注意与时间惩罚重复计权。罚项尺度事先固定，不为赢某一条真实轨迹而调参。
- 保留四项奖励分解，逐环境报告每项贡献；不能仅总回报变好就接受更高业务延迟。

### D. 修复选模和训练覆盖

默认仍保持每环境1/13。可比较“独立有放回抽样”与“每13回合随机打乱、各一次”的覆盖方案；后者边际仍均匀，但不再独立。若采用，checkpoint必须保存当前排列、游标和RNG，恢复结果与连续训练一致。

- NATIVE提高至20%–30%只作为额外消融，不能默改默认；开发/测试最终仍报告13环境等权宏平均、逐环境和最差环境。
- 候选选择先满足逐环境业务约束，再比较宏平均回报/C。建议以逐环境`C_PPO <= C_Stay`、失败率不增加作为首轮开发约束；若因测量噪声需容忍带，必须在独立验证前冻结并报告，不能看完测试再放宽。
- 没有合格策略就明确“未找到候选”，不把初始或失败策略包装成已选合格模型。
- 迁移总数、涉及请求数、重复/反向迁移、主动Stay和合法机会必须进入选模报告；不以迁移成功率替代收益。
- 初轮保留现有13动作网络。单Categorical的动作熵不等于Stay/Migrate探索充分；如后续独立消融二级门控，须重做联合logp、Mask、entropy与checkpoint合同，不能只在部署后处理动作。
- 冻结模型后先短训、看逐环境进展，再决定是否延长；总预算沿用或低于现有配置，不默认重复492次长训。

### E. 独立验证与判定

本次真实pilot已用于诊断，若再参与拟合即为开发数据。新留出trace不得用于阈值、权重或checkpoint选择。

主机阶段执行CPU验证；未来真实测试沿用每轮200秒、主测一组、必要时一组反序/备选，备选仍不通过就跳过下一环境的规则，不扩为长时间扫参。越窗、审计未过、缺终止证据的结果保留诊断，排除正式均值；严格报告有效环境覆盖，不能只删除失败项后宣称全13项通过。
