## 一、唯一目标和范围

**以最低时间成本，找到一个迁移后真实服务变好、迁移机会充足、每轮有足够多不同请求成功迁移的环境，供后续 PPO 学习。找到一个就结束本轮搜索。**

**用户明确指定模型为 Qwen2-1.5B。本轮所有预热、P0、P1 和备选实验均使用该模型，不得换成 0.5B 以缩短时间或获取正收益。**

本轮是快速筛选，不是论文最终实验。允许集中测试人工热点，但必须明确适用范围。不要顺便实现仿真、收益预测器、修改奖励、改 PPO 网络、训练 PPO或扩大扰动矩阵。不把“代码已写好”当作真实实验完成。

必要认识：PPO 不是按动作频率直接增加权重。仅 Stay 合法的样本不会直接提高 Stay 的 actor 概率，但会消耗采样预算；可以迁移却选择 Stay 的样本仍是必要的学习数据。本轮通过寻找机会丰富的环境减少无效等待，不强迫迁移，不要求迁移动作占全部时间步的多数。

## 三、时间预算和停止规则

- 目标：把本批集群实验控制在约 30–45 分钟；这是时间预算目标，不再用 0.5B 的轮长推断 1.5B 耗时。根据首个 1.5B 完整回合更新剩余运行时间估计，预算不够即交付 incomplete。
- 从开始启动集群计时，默认 **45 分钟停止启动新回合**；预计剩余预算不足 8 分钟时不启动新回合，先收尾已启动请求。
- 一次启动，尽量保持四个模型实例驻留，轮间排空并检查没有遗留迁移。
- 标准路径：预热一次＋6 个正式回合。仅在 Q15-A 明确未达标且剩余预算充足时尝试 Q15-B，正式回合总数最多 10。
- 完整回合不因接近预算被悄悄截短。若出现持续故障、120 s 无请求输出进展或总时间超过 60 分钟，可停止本任务拥有的服务以收尾，相关回合标为 aborted/incomplete，保留全部失败证据，不纳入成功比较。
- 8 分钟是启动前的预算预留，不是从性能统计删除慢请求的截止时间。
- 服务启动最多等待 8 分钟。现有 `wait_service_ready` 未必强制实施启动超时，快速入口需要明确加上总等待限制。
- 出现第一项生命周期、路由、执行或数据审计失败时，停止后续正式比较；允许一次明确有原因的小修复和新运行目录重试，不做无解释的重复重启。
- 若找到一个达标环境，立即结束，不继续找更大提升。

这些限额属于新实验计划，不重置或继续消耗旧 PPO 训练目录的预算。

## 四、冻结首选配置

确认本机 Qwen2-1.5B 可运行，冻结以下探索配置，不将其称为历史复现：

| 项目 | 设置 |
|---|---|
| GPU/实例 | 4×RTX 3060 12 GiB；四副本，每副本 TP=1 |
| 模型 | 本地 `model/Qwen/Qwen2-1.5B`，half，eager；tokenizer 与模型来自同一目录 |
| 上下文/并发 | max_model_len=2112，max_num_seqs=128 |
| KV 配额 | gpu_memory_utilization=0.65；记录实际分配块数 |
| batch token 上限 | 显式 max_num_batched_tokens=2112，记录实际生效值；不是历史 1.5B 扫描的 4096 配置 |
| 迁移/输出通路 | rayrpc、SR、rayqueue；Ray CPU=16 |
| 请求批量 | 每轮 128 个，输入 128 token，实际输出 1536 token |
| 生成 | temperature=0，ignore_eos=true，n=best_of=1；按 tokenizer 验证输入和实际输出 |
| 初始路由 | 约 90% 请求固定到一个热点实例，其余分散；直接复用 `make_trace` 的整数分配规则 |
| Q15-A 到达率 | 1.0 req/s，按现有生成器在 [0,128 s] 内抽取 128 个时间点 |
| Q15-B 到达率 | 0.6 req/s，到达时间区间 [0,128/0.6 s]，其余设置不变 |
| 控制周期 | 约 1 s，记录实际间隔 |
| Balanced | 复用 `balanced_action` 的选择与迁后检查；阈值按下面容量规则冻结，不能使用写死的 9000 |
| 保护 | 全局最多一个迁移；终态后冷却 5 s；新鲜度 2 s；容量余量使用已有检查 |

这里的 1.0/0.6 req/s 是预注册探索值，**不是 1.5B 实测饱和率的某个比例**。复用 `make_trace` 时可设置 family=S1、profile=decode1536、rho=1、lambda_ref=选定请求率、hot_fraction=0.9；注明此处 lambda_ref 仅作为生成器的速率参数，不是经过校准的服务能力。

阈值规则在实验前固定：预热排空后读取四实例实际 `total_blocks`，令 `F_threshold=min(total_blocks_i)/8`，将实际数值和来源快照写入 plan 后冻结；Q15-A/Q15-B 及两个种子共用。这里的 8 是本次探索选定的容量/请求尺度，不保证有效。其目的在于避免直接照搬 0.5B 的 9000 后，只剩完全空闲目标能接收迁移。若实例容量未知/为零则停止；若实际合法机会充足但该阈值过滤了大部分动作，明确报告这一瓶颈，不在同一次试验中自动改阈值追求通过。

注意 `full_completion.run_episode` 的 Balanced 分支目前写死 `threshold=9000.`。快速入口须显式传入本轮冻结阈值；可增加一个默认仍为 9000 的可选参数以保留旧行为，同时保存实际生效阈值并测试其传递。不能只改 YAML 而执行器仍用旧值。

新建运行目录，复制所需配置并把路径指向本次文件，不修改旧实验文件。配置中表面上启用 routine migration 并不证明实际会自主迁移：检查桥接控制 lease 如何禁止原生常规迁移，并在 Stay 回合实证确认成功迁移为零。若存在两套调度同时下发，修复隔离后重新开始，不能混算。

初始路由要核对首次 engine admission，不能只看客户端写了什么。实例 ID/epoch 的映射须在配对期间稳定；记录实际 worker PID→GPU UUID 映射，不把实例列表顺序默认当物理卡号。

## 五、P0：最低限度的可信对照

目的：确认开启 PPO 的观测、网络前向、日志路径本身没有制造大幅性能差异。本轮不做原生 OFF 与全部部署方式比较，使用已有同桥接 Stay 作为主要对照。

准备两种运行模式：

- `Stay`：复用已有完整回合 Stay，照常采集状态、心跳和事件，不提交迁移。
- `PPO-STAY`：CPU 执行当前观测转换、actor/critic 前向和对应决策日志，但执行动作固定为 Stay，不更新参数。

PPO-STAY 的记录必须分清 `suggested_action` 与 `executed_action=0`，标注 `measurement_only=true`，不能伪造“执行 Stay 是按原策略采样”的 log-prob，也不能将此数据作为 PPO rollout。若接口要求 `action` 字段，传入执行动作 0，原分布建议另存。不调用 `build_rollout` 或训练入口。

可使用冻结历史 checkpoint；若读取复杂，允许固定随机种子实例化同一网络做前向开销检查。后者只能称“网络路径开销检查”，不能称完整复现历史策略。四张卡不用于网络训练或推理，`torch_num_threads=1`。

### 标准运行顺序

两个新种子建议 `141101`、`141102`。先检查现有账本；若已使用则换为未使用种子并在运行前冻结。每个种子的输入 trace 生成一次后复用，输出哈希。

| 序号 | 场景/种子 | 模式 | 用途 |
|---|---|---|---|
| 0 | 独立预热 | Stay | 复用四实例各一次短请求预热，不计正式统计 |
| 1 | Q15-A / seed1 | Stay-A | P0 起始对照，同时复用为 P1 对照 |
| 2 | 同一 trace | PPO-STAY | P0 网络路径开销 |
| 3 | 同一 trace | Stay-B | 检查漂移，复用为 P1 对照 |
| 4 | 同一 trace | Balanced | P1 第一个配对结果 |
| 5 | Q15-A / seed2 | Balanced | 反转顺序，P1 第二个结果 |
| 6 | 与第 5 轮同 trace | Stay | P1 第二个对照 |

每轮结束排空、核对请求和迁移终态，再开始下一轮。同一 seed 的模型、路由、生成参数与请求内容保持一致。

### P0 快速门槛

用 cost=(mean E2E+CVaR95 E2E)，不需要新的 T_ref；同一场景配对的归一化常数会抵消。另报 mean、P95、TTFT/TPOT 和发包延迟。

- 三轮均完成 128/128 请求，路由/生命周期审计通过，没有真实迁移和错误。
- `abs(cost_A−cost_B)/mean(cost_A,cost_B)≤5%`，平均 E2E 使用同样的漂移检查。
- `abs(cost_PPO-STAY−mean(cost_A,cost_B))/mean(cost_A,cost_B)≤5%`，平均 E2E 使用同样检查。
- PPO-STAY 的 P95 E2E 相比两个 Stay 的平均值恶化不超过 10%。
- 分开记录 CPU 前向/特征开销与完整控制周期；不要把控制周期全部算作神经网络耗时。

这些是**工程筛选门槛，不是统计等价结论**。不足以证明所有负载下都没有控制开销。若失败，不继续筛选或训练；先报告差异及已观测原因，最多做一次明确修复。

## 六、P1：同时检查“确有收益”和“机会够多”

第一个种子以 Stay-A 与 Stay-B 各项指标的平均值作为预注册对照；同时公开 Balanced 相对两个 Stay 分别的变化。第二个种子使用其配对 Stay。不把两次相同 seed 的 Stay 当两个独立种子。

本轮主收益指标固定为 cost=(mean E2E+CVaR95 E2E)；同时要求平均 E2E 改善。相对改善统一计算为 `(Stay−Balanced)/Stay`。不要改用恰好获胜的 GPU 均衡度、某个分位数或迁移数量。

### 必须从每轮 decisions/migrations 计算的数量

| 名称 | 定义 |
|---|---|
| 总决策 N_all | 请求全部结束前的决策，预热/收尾后空循环不计 |
| 有选择机会 N_opp | 当时原始 mask 中，除 Stay 外至少一个迁移动作合法 |
| 只能 Stay N_forced | N_all−N_opp |
| 自愿 Stay N_voluntary | 有迁移动作合法但选了 Stay |
| 选择迁移 N_move | 实际发出的非零迁移意图，不是网络 shadow 建议 |
| 机会占比 | N_opp/N_all |
| 有机会时迁移比例 | N_move/N_opp；分母为零写 N/A |
| 成功次数 | 与 coordinator 真实终态对应的成功 migration_id 数，去重 |
| 不同请求覆盖 | 成功迁移的 distinct request_id/128 |
| 成功迁移频率 | 成功次数/从首个实际发包到最后完成的分钟数 |
| 重复/反向迁移 | 同请求多次迁移、原方向回迁分别统计 |

另外按 busy、冷却、源无候选、目标空间不足、状态陈旧等记录无机会原因。如果原始日志没有现成原因，可调用同一检查函数或从 snapshot 派生，但不得用事后状态覆盖当时 mask。各原因可以重叠，不强行相加成 100%。

约 5 s 冷却会自然产生大量只能 Stay 的时间步。只要有足够成功迁移和不同请求覆盖，就不因总体动作中 Stay 占 80%–90% 而直接判失败。

### 运行前冻结的通过条件

以下门槛服务于低成本训练候选筛选，不是普适最优值。只用两个新种子，不在本轮宣称统计显著：

1. P0 快速门槛通过。
2. 两个种子的 Stay/Balanced 均完整服务 128 个请求，实际长度核对正确，路由和迁移审计通过；无请求错误、未知迁移终态和策略外迁移。
3. 每个种子的 cost 与平均 E2E 改善均大于 0；两个种子的平均相对改善分别至少 5%。
4. 第一个种子的 Balanced 相比 Stay-A、Stay-B 各自的 cost 均更低，避免通过挑选较差的一次 Stay 获胜。
5. 每个种子的 P95 E2E 恶化不超过 5%；P95 TTFT、P95 TPOT 恶化不超过 10%。超出时报告权衡，不能称为本协议通过。
6. 每个 Balanced 回合成功迁移至少 20 次，不同请求覆盖至少 15%，成功迁移频率至少 3 次/分钟，`succeeded/started≥90%`；rejected 另报，不混入 started。
7. 每个配对 Stay 回合至少 30 个有选择机会，机会占比至少 20%。Balanced 的机会比例可能因 busy/冷却变小，单独报告，不要求它与 Stay 相同。

本任务只证明“该受约束 Balanced 在该环境里的整体迁移策略有收益”，不能推出每次迁移都有效，更不能证明 PPO 已可学会或已优于它。若只有均衡指标改善或迁移很多但服务变慢，则判失败。

### 唯一备选与提前停止

- Q15-A 第一个种子通过收益/机会检查，才进入第二个种子。
- 若 Q15-A 第一个种子收益明确为负或机会不足，保留结果；预算足够则转 Q15-B，执行 seed1 Stay/Balanced、seed2 Balanced/Stay，最多四轮。不重跑 Q15-A 直到变好。
- 若 Q15-A 第一个种子为正、第二个未通过，则报告不稳定；剩余预算允许才测试 Q15-B，否则结束为 not_found/inconclusive。
- Q15-B 只复用已完成 P0 的控制路径检查，明确这是对另一请求率的有限外推，并核对其发包延迟和控制开销；若开销明显变化则标为待补 P0，不能强行通过。
- 不增加第三候选，不改冷却、已冻结阈值、模型、请求数量或输出长度来追求达标。若两个候选均不满足，交付失败原因和下一次最值得测试的一项；不得自动退回 0.5B。

## 七、实现要求与最少验证

建议新增一个薄入口 `benchmark/run_p0p1_fast.py`，提供 `plan`、`run`、`analyze`；这些是本次待实现接口，不是假定现成命令。也可扩展已有入口，前提是默认不启动旧的大矩阵。

要求：

- `plan` 只生成/验证配置、trace、预算和代码指纹；不启动 GPU。
- `run` 只执行冻结序列和条件分支；拥有服务启动/停止生命周期；结束时清理本任务进程并检查 GPU/Ray 状态。
- `analyze` 不启动服务，仅从本次原始账本重建报告；绝不把历史数据与新结果混成两个确认种子。
- 同一运行目录不覆盖原始失败结果；重试新建 attempt 或新目录并记录原因。
- 若同路径重复耗时，优先精简本次日志读取/后处理，不删除迁移事件和生命周期证据。
- 主服务正常退出、异常和用户停止均有清理路径；不能杀死别人的 GPU/Ray 进程。

最少 CPU 验证：

1. 固定 seed 两种策略复用相同 trace/hash，预期路由及实际 token 长度正确。
2. 测量专用 PPO-STAY 不执行任何迁移、不触发训练，建议/执行动作分开保存。
3. 用小 fixture 验证“只能 Stay / 自愿 Stay / 迁移”的分母、去重和不同请求覆盖率。
4. 预注册收益门槛对正例、负例、缺数据、零分母、失败回合判定正确。
5. 验证预算不足不再开启新回合，以及异常后调用本任务服务清理。
6. 验证 API 模型路径、tokenizer、实际 batch 参数均匹配冻结的 1.5B 配置；Balanced 分支确实使用本轮容量规则产生的阈值，旧调用的默认值保持不变。

只运行相关现有回归和上述必要测试，不为本轮增加通用平台或全仓测试工程。

## 八、交付文件和最终回答

所有结果写入新目录：`benchmark/results/p0p1_fast_<timestamp>/`。

至少包含：

- `plan.json`：目标、首选/备选、配置、种子、顺序、门槛、预算、版本和哈希。
- `environment_audit.json`：GPU/进程/版本/实际参数/卡映射。
- `runtime_config.yaml`、服务配置、冻结 `traces/`。
- 每轮原始请求、决策、迁移、审计和 `episode.json`；可在读回校验后压缩。
- `results.csv`：每轮 mean/P95/CVaR、TTFT/TPOT、完整率、发包偏差、决策/机会/迁移统计。
- `comparison.json`：每个种子的各项改善、P0 偏差与所有门槛判定。
- `training_environment_handoff.json`：推荐配置及完整复现参数、适用范围、机会/迁移数量、证据路径；没有通过就 `recommended=false`，不填虚构环境。
- `report.md`：通俗结论、结果表、真实用时、未完成项、清理结果。

只有逐项通过才写 `fast_candidate_passed`。预算不足、执行失败、结果不稳定分别标记，不能统一写 passed。本轮不声称“完整科研版 P0/P1 已完成”。

最终向用户回答以下四件事，少用术语：

1. 找到了没有？用什么模型、长度、请求率和热点比例？
2. 两个新种子各快了多少？每轮成功搬了多少次，覆盖多少不同请求？
3. 能迁移的机会有多少？大量 Stay 中多少是因为当时根本不能搬？
4. 总共花了多久，结果文件在哪里，是否值得进入下一步 PPO？

不要因为用户希望迁移多，就加迁移奖励、强迫随机搬请求或暗中缩短冷却。任务成功的标准是“真实改善＋机会充足”，不是把 Stay 比例做小。
